# Retroid Pocket 5 Vulkan startup investigation

The logs from TotK Fork 1.2.0-beta.2 make unsupported shader subgroup operations the strongest lead for issue #2. The fork has a concrete capability-check gap, and a different port reproduced a matching Vulkan validation error on another Adreno 650. The report from this fork identifies where it observes device loss and leaves the triggering shader and the device’s memory state open. [Issue #2 report](https://github.com/GTomasel/totk-android-low-ram/issues/2#issuecomment-7143170038) · [Attached launch log](https://github.com/user-attachments/files/35372637/totk.log)

## What the existing launches establish

The attachment contains an older launch and nine beta.2 launches. Each beta.2 launch reused a valid game-data verification record, initialized Vulkan, rendered and returned `VK_ERROR_DEVICE_LOST` from a GPU fence wait. With bundled Turnip (`3e8621cc0e`), the reporter saw a black screen before returning to the launcher. With TurnipZ 0.4 (`3228709760`), the reporter saw the game menu briefly. `Copy` selected readback presentation, and `Sysmem` appeared in the effective Turnip environment. Neither was sufficient, alone or together, on either driver. The fence's submission number is where the host received the error. Asynchronous GPU work means it does not identify the responsible command by itself. [Launch log](https://github.com/user-attachments/files/35372637/totk.log) · [Vulkan device loss](https://docs.vulkan.org/spec/latest/chapters/devsandqueues.html#devsandqueues-lost-device)

All nine launches reported the same subgroup capabilities, `supportedStages=0x20`, `supportedOperations=0x67f` and native size 128. `0x20` is the compute-stage bit. The distinct `requiredSubgroupSizeStages=0x30` value describes the stages for subgroup size control. It does not extend the set that can use subgroup operations, and the advertised 64–128 range cannot pin a native 32-wide subgroup. Turnip's source starts with compute support and adds graphics support when the GPU has the needed `getfiberid` capability. The two beta.2 drivers both advertised compute only. Changing drivers within this capability profile leaves that constraint in place. [Turnip capability reporting](https://chromium.googlesource.com/external/gitlab.freedesktop.org/mesa/mesa/+/refs/heads/upstream/main/src/freedreno/vulkan/tu_device.cc) · [Vulkan subgroup size properties](https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceSubgroupSizeControlProperties.html) · [Vulkan shader stage bits](https://docs.vulkan.org/refpages/latest/refpages/source/VkShaderStageFlagBits.html)

The log has guest memory accounting and renderer retention estimates. The guest's `Total Available Memory` describes the emulated guest limits. The descriptor estimate and staging retention settings cover individual subsystems. The attachment has no contemporaneous process RSS/PSS, system memory headroom, Vulkan heap budget or Android process-exit evidence. It offers no direct support for an Android low-memory kill. Every beta.2 crash shows the game receiving the Vulkan error and handing it to the launcher. Memory pressure could still contribute to a GPU-side fault, which these samples cannot distinguish. [Launch log](https://github.com/user-attachments/files/35372637/totk.log) · [Android process exit reasons](https://developer.android.com/reference/android/app/ApplicationExitInfo#REASON_LOW_MEMORY)

## Shader compatibility and upstream evidence

- The original port aggregates an Adreno 650 title-screen report and an AYN Thor Lite intro crash in issue #10. The reports describe similar failures across multiple drivers and lack logs. [Original port tracking issue](https://github.com/AurelioB/totk-android/issues/10) · [Thor Lite report](https://github.com/AurelioB/totk-android/issues/51)
- In TOTKDroid issue #8, a Galaxy Z Fold2 with Snapdragon 865+, Adreno 650 and Android 13 reported exactly the same stage mask, operation mask and subgroup width as our Retroid. Khronos validation caught `OpGroupNonUniformBallot` in a fragment shader on that compute-only subgroup configuration. The contributor used a single-invocation path for the visibility-counter reduction, where each passing fragment atomically counts itself. They reached the opening cave cutscene on two Turnip builds. The contributor did not verify full gameplay. The specification forbids subgroup-scope group instructions in an unsupported stage. [Validation report and Fold2 test](https://github.com/mamcjr/TOTKDroid/issues/8#issuecomment-6595622022) · [VUID-RuntimeSpirv-None-06343](https://docs.vulkan.org/spec/latest/appendices/spirvenv.html#VUID-RuntimeSpirv-None-06343)
- TOTKDroid 0.3.0-beta shipped a stage-aware Maxwell translation and separated the selected path in its cache. Its renderer translates Maxwell instructions directly, while our fork loads multiple variants of pretranslated SPIR-V. The other renderer's source illustrates a compatibility strategy. A general singleton rewrite changes the result of inter-lane votes and shuffles and needs shader-specific evidence before use here. The other port's Adreno 618 logs subsequently passed the prologue and encountered a separately diagnosed `VK_ERROR_OUT_OF_DEVICE_MEMORY` with its GPU game-memory option enabled. [Stage checks](https://github.com/mamcjr/TOTKDroid/blob/v0.3.0-beta/runtime/nvn/vulkan/device.c#L688) · [Maxwell translation and singleton path](https://github.com/mamcjr/TOTKDroid/blob/v0.3.0-beta/runtime/nvn/maxwell/translate.c#L2264) · [Adreno 618 follow-up](https://github.com/mamcjr/TOTKDroid/issues/40#issuecomment-6904056449) · [Separate allocation failure](https://github.com/mamcjr/TOTKDroid/issues/60#issuecomment-6904066799)
- In beta.2, the fork checks the subgroup capability in `shader_postprocess` only when the experimental `TOTK_VK_SUBGROUP_FIX` switch is on. All ten launches logged it off. The switch attempts to preserve Maxwell logical 32-lane groups on devices with subgroup support in the shader's stage. It refuses rewritten modules if the stage lacks support. The project's earlier 1.4.3 host census recorded subgroup instructions in 22 fragment, 11 vertex and 5 compute modules of a prepared loose seed. This establishes exposure to the capability gap. The reporter uses an indexed pack and the beta.2 logs do not map the failing submission to modules, so the census cannot identify the exact opening shader in this run. [Beta.2 shader path](https://github.com/GTomasel/totk-android-low-ram/blob/v1.2.0-beta.2/games/totk/android/gfx/vk_shader.c#L469) · [Seed census and rewrite behavior](https://github.com/GTomasel/totk-android-low-ram/blob/v1.2.0-beta.2/games/totk/android/VULKAN.md#logical-32-lane-subgroups-experimental)

Two fragment shader keys marked for title-screen, menu or save-list use in the fork's own manifest are `8396359d…` and `9a5e3335…`. Translating their source from an existing local 1.4.3 dump yielded the same election-and-add pattern in both. They ballot a constant true predicate inside the eligible-fragment branch, find the highest set bit and use that lane to atomically add the population count at a constant buffer offset. The returned atomic value is unused. The second module performs this at two separate offsets and has other atomic adds outside the election branches. For each reduction, one add per eligible invocation preserves the sum at that offset. The broader local sample included 15 fragment modules using subgroup instructions or votes across the application and system shader packages, including shuffles whose semantics require a separate solution. The host manifest records use by an earlier title/menu capture, while the reporter's exact driver submission remains unobserved. [Title shader manifest entries](https://github.com/GTomasel/totk-android-low-ram/blob/v1.2.0-beta.2/games/totk/assets/shader_list.tsv#L58149-L58150) · [Manifest format](shader-list.md#what-is-in-it)

The current-source Vulkan translation service reproduced these operations in four manifest binding variants of the two title keys. The first shader uses one ballot. The other three variants each use two. The source key is a hash of the local Maxwell code and NVN control bytes, which matched the title manifest. The four unmodified modules passed generic Vulkan 1.3 SPIR-V validation. Device-specific validity still depends on the actual shader-stage properties at pipeline creation. [Vulkan runtime SPIR-V stage requirement](https://docs.vulkan.org/spec/latest/appendices/spirvenv.html#VUID-RuntimeSpirv-None-06343)

The same sample includes a counter that illustrates the limit of a singleton fallback. Shader `d67bc5cb…` uses the same ballot, lane election and atomic sequence, but the elected fragment's position contributes to the counter index. Letting every fragment count itself could distribute increments across different counters. A valid-looking opcode sequence alone is insufficient evidence that the replacement preserves the shader's output.

The defensible compatibility change is automatic stage and operation validation for translated shaders, including pair-specific vertex variants. Fallbacks need to preserve the actual shader's semantics, with an identified shader or proofs for a restricted instruction pattern. Unsupported shaders that cannot be translated safely should produce a bounded diagnostic. A launch that survives by skipping a draw still needs a visual and gameplay check. Phase labels, shader keys, stages, lowering/refusal reasons and submission breadcrumbs let a single failed launch identify the next shader to inspect. [Vulkan SPIR-V runtime requirements](https://docs.vulkan.org/spec/latest/appendices/spirvenv.html#VUID-RuntimeSpirv-None-06343) · [Existing Android shader path](https://github.com/GTomasel/totk-android-low-ram/blob/v1.2.0-beta.2/games/totk/android/gfx/vk_shader.c)

## What one launch can capture

| Signal | Interpretation and limits |
| --- | --- |
| System `MemAvailable`, swap, app `VmRSS` and `VmHWM`, anonymous/file/shared RSS and swap, app PSS when available | Capture inexpensive counters at startup milestones and periodically. Include the most recent observations and a best-effort fatal snapshot. `smaps_rollup` or Android's process memory API can provide slower PSS samples. Record missing fields as unavailable. [Linux `/proc`](https://docs.kernel.org/filesystems/proc.html) · [Android system memory info](https://developer.android.com/reference/android/app/ActivityManager.MemoryInfo) |
| Vulkan heap flags, usage, budget, and exact result for failed allocation operations | `VK_EXT_memory_budget` is advertised in Turnip's upstream device table. Its values are estimates per heap and may change. On a unified-memory device they describe another view of overlapping memory, so adding them to process RSS overstates total usage. [Turnip extension table](https://chromium.googlesource.com/external/gitlab.freedesktop.org/mesa/mesa/+/refs/heads/upstream/main/src/freedreno/vulkan/tu_device.cc) · [Vulkan memory budget](https://docs.vulkan.org/refpages/latest/refpages/source/VkPhysicalDeviceMemoryBudgetPropertiesEXT.html) |
| Android historical exit reason, PID, timestamp and last sampled RSS/PSS | API 30+ allows an app to query its own process exits. Read it after the game process has died and correlate it to the launch, retrying on a subsequent export or launch if Android has not recorded it yet. Zero RSS/PSS can mean unsampled. On some devices a low-memory kill is only reported as `SIGKILL`. [Android exit API](https://developer.android.com/reference/android/app/ActivityManager#getHistoricalProcessExitReasons(java.lang.String,int,int)) · [Exit sample semantics](https://developer.android.com/reference/android/app/ApplicationExitInfo#getPss()) |
| Last submitted and completed serials, frame/stage markers and recent shader or pipeline keys | These can distinguish activity close to the failure from the fence that surfaced it. Keep recording bounded to avoid altering timing materially or exhausting the retained launch log. [Vulkan debugging](https://docs.vulkan.org/spec/latest/chapters/debugging.html) |
| Optional Vulkan fault details | Negotiate `VK_EXT_device_fault` or its successor when advertised, and query fault information only through the supported interface. The upstream Turnip device table inspected here does not advertise the extension. Keep app-side diagnostics when the driver can only return `VK_ERROR_DEVICE_LOST`. [Vulkan fault extension](https://docs.vulkan.org/refpages/latest/refpages/source/VK_EXT_device_fault.html) · [Turnip extension table](https://chromium.googlesource.com/external/gitlab.freedesktop.org/mesa/mesa/+/refs/heads/upstream/main/src/freedreno/vulkan/tu_device.cc) |

KGSL can record an IOMMU page fault, GPU or GMU reset and hardware snapshot in the kernel. A stock app cannot rely on access to those logs or vendor sysfs nodes. Standard app logs should keep diagnostic measurements and identifiers needed to connect events, without copying raw system logs or memory. Privileged ADB capture is useful on a maintainer-owned device if the firmware allows it. [KGSL IOMMU source](https://android.googlesource.com/kernel/msm/+/a90ae1f90459bf8188c7e4455f3c724a765579dc/drivers/gpu/msm/kgsl_iommu.c) · [KGSL snapshot source](https://android.googlesource.com/kernel/msm/+/b295e3df6bd5591086e58a323f35c9d60630c924/drivers/gpu/msm/kgsl_snapshot.c) · [Android log access](https://developer.android.com/privacy-and-security/risks/log-info-disclosure)

## Retroid confirmation

One launch on the next instrumented build with a driver and settings already tested in beta.2 is enough for the first comparison. The existing log serves as baseline. Export one `totk.log` after returning to the menu or after reaching the title and loading a save if the game proceeds. The most informative outcomes are which shaders were lowered or refused before the failure, whether the original transition now works, and whether allocation or memory-pressure evidence accompanies a later failure. Run any further setting comparison only after that evidence identifies a specific path worth isolating.
